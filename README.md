# order-management-agent

### Правила в коде

| Инструмент | Правило |
|---|---|
| `cancel_order` | отменяются только `placed`/`assembled`, оплата возвращается целиком; начатая индивидуальная сборка не отменяется ни в каком статусе (проверка стоит **до** проверки статуса); `cancelled` → «уже отменён»; в доставке → подсказка «отказаться при получении»; `delivered` → подсказка «оформить возврат» |
| `change_address` | только `placed`/`assembled`, пустой адрес отклоняется |
| `create_refund` | только `delivered`, не позже 14 дней с получения (14-й день включительно), сумма > 0, **уже возвращённое + новая сумма ≤ оплаченного** (частичные возвраты можно, двойной — нет) |

Разрешено только явно перечисленное: неизвестный статус = отказ. При отказе ничего не меняется,
модель получает `{"error": "причина. что предложить клиенту"}`, а не исключение.

### Решения

- **Подтверждение перед действием.** Бот повторяет данные из `get_order` и выполняет отмену/смену адреса/возврат
  только после «да». Ловит ошибки понимания (не тот номер, не та сумма). Правило мягкое (в промпте), жёсткие
  правила — в коде.
- **История сохраняется после каждого шага**, а не в конце хода, и **шаг пишется вместе с заказами одной
  транзакцией** (`store.save_step`). При падении посреди хода история и состояние заказов не расходятся,
  а `function_call` никогда не остаётся без `function_call_output`.
- **Системный промпт в `instructions`, а не в истории:** новая версия промпта действует и в старых сессиях,
  в базе нет дублей. Дата «сегодня» стоит в конце промпта, чтобы не ломать кэш префикса.
- **Инструменты одного шага выполняются по очереди:** они меняют общее состояние заказов.
- **Заказы хранятся в SQLite снимком (JSON),** а инструменты работают со словарями в памяти — компромисс курса.
  В реальном сервисе это была бы таблица заказов с транзакциями и блокировкой строк.

## Запуск

```bash
pip install -r requirements.txt
cp .env.example .env            # вписать OPENAI_API_KEY
python chat_cli.py              # консольный чат
uvicorn server:app --port 8000  # сервис, Swagger: http://localhost:8000/docs
python run_dialogs.py low       # 10 диалогов → dialogs/dialogs_low.md
```

API: `POST /sessions` (заголовок `X-User-Id`) → `session_id`; `POST /sessions/{id}/messages` `{"text"}` →
поток SSE (`tool`, `delta`, `done`, `error`); `GET /sessions/{id}/messages` → история и цена сессии.

pytest checks/test_cancel_order.py

## Десять диалогов

Таблица: [`dialogs/dialogs_low.md`](dialogs/dialogs_low.md) (полный журнал — `dialogs/results_low.json`).
Сценарии: две отмены (с возвратом и без оплаты), смена адреса, возврат, отказы по правилу (индивидуальная сборка,
истёкший срок, заказ в доставке), несуществующий заказ, частичный возврат, клиент не подтвердил отмену.
Каждый диалог начинается с исходного состояния заказов и проверяется по статусу, возвратам и адресу после диалога.
**Результат: 10/10.**

## Цена одного диалога

Цена считается по `usage` каждого запроса к модели (`common.cost_usd`): обычный вход, кэшированный вход и выход
по прайсу модели `gpt-5.6-luna` из курса — $0.20 / $0.02 / $1.20 за 1M токенов (сентябрь 2026).

| effort | верно | запросов к модели | всего за 10 диалогов | **за диалог** |
|---|---|---|---|---|
| **low** | 10/10 | 36 | $0.008536 | **$0.00085** |
| medium | 10/10 | 36 | $0.008771 | $0.00088 |

Типичный диалог — 2 хода клиента и 3–4 запроса к модели: `get_order` → подтверждение → действие → ответ.

## Выбранный effort: `low`

- **Точность одинаковая:** 10/10 на обоих уровнях, правила обеспечивает код, а не рассуждение модели.
- **`medium` дороже на ~3% и качество ответов не улучшил.** Обе слабые формулировки (ниже) остались;
  в диалоге 7 `medium` на «да» даже предложил «оформить возврат несмотря на истёкший срок», чего сделать нельзя.
- Задачи агента короткие: прочитать заказ, сверить с просьбой, вызвать один инструмент. Глубокое рассуждение
  здесь не нужно, а лишние reasoning-токены оплачиваются как выход.
